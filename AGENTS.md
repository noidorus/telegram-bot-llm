Назначение проекта

Telegram-бот принимает текстовое сообщение пользователя, передаёт его в отдельный inference-сервис с языковой моделью и возвращает результат обратно в Telegram.

Текущая схема:

Telegram → Bot Process → HTTP → Inference Process → LLM → HTTP → Bot Process → Telegram

На текущем этапе память диалога отсутствует.

Каждое сообщение является независимым запросом к LLM.

Архитектура

Проект состоит минимум из двух независимых процессов.

Telegram Bot

Отвечает за:

получение Telegram updates;

извлечение текста сообщения;

вызов inference API;

отправку ответа пользователю;

обработку ошибок Telegram API и inference API.

Inference

Отвечает за:

HTTP API для генерации ответа;

валидацию запросов;

выбор LLM provider;

вызов конкретной модели;

обработку ошибок inference.

Telegram Bot не должен знать детали Ollama или конкретной LLM.

Связь между процессами осуществляется только через HTTP API.

Inference должен иметь возможность быть остановлен, перезапущен или заменён независимо от Telegram-процесса.

LLM Provider

Inference должен использовать абстракцию provider.

Принцип:

Inference API
      ↓
LLM Provider
      ↓
Ollama

Ollama является реализацией provider, а не частью Telegram-бота.

Модель должна задаваться через конфигурацию.

Например:

LLM_PROVIDER=ollama
LLM_MODEL=qwen3:1.7b
LLM_BASE_URL=http://localhost:11434

Не привязывай бизнес-логику к конкретной модели.

В дальнейшем должна быть возможность добавить другой provider без изменения Telegram-бота.

Telegram

Используй Telegram Bot API напрямую через HTTP.

На текущем этапе достаточно:

getUpdates;

long polling;

offset;

sendMessage.

Бот должен:

получить update;

определить текстовое сообщение;

получить chat_id;

передать текст в inference API;

получить ответ;

отправить ответ в тот же Telegram chat.

Updates без текстового сообщения должны игнорироваться.

Ошибка обработки одного сообщения не должна останавливать polling.

Ошибка Telegram API также не должна завершать процесс бота.

Контекст

История сообщений не сохраняется.

Не добавляй:

БД;

Redis;

session storage;

chat history;

memory;

embeddings;

RAG.

Каждый запрос должен иметь форму:

User Message
     ↓
LLM
     ↓
Bot Reply

Если в будущем потребуется память — это будет отдельная задача и отдельное архитектурное решение.

Конфигурация и безопасность

Все настройки должны передаваться через environment variables.

Секреты запрещено:

хранить в исходном коде;

коммитить в Git;

выводить в логи.

Обязательные секреты и настройки должны быть описаны в .env.example.

.env должен находиться в .gitignore.

При отсутствии обязательной конфигурации приложение должно завершаться с понятной ошибкой.

TypeScript

Используй строгую типизацию.

Предпочитай:

небольшие функции;

явные типы;

интерфейсы для API;

минимальную связанность компонентов;

понятные модели данных.

Не используй any, если можно определить тип.

Не скрывай проблемы типизации через as any.

Не создавай сложную архитектуру заранее.

Ошибки

Ошибки Telegram API, inference API и LLM provider должны обрабатываться независимо.

Падение LLM не должно приводить к падению Telegram polling.

Падение одного запроса не должно останавливать обработку следующих сообщений.

HTTP API inference должен возвращать структурированные ошибки.

Не раскрывай пользователю внутренние детали инфраструктуры.

Ollama provider;

ошибки inference;

При изменении поведения добавляй или обновляй соответствующие тесты.

OpenSpec

OpenSpec является источником истины для текущей реализации.

Перед началом работы:

Прочитай proposal.md.

Прочитай соответствующие spec.md.

Прочитай design.md.

Прочитай tasks.md.

Определи текущую незавершённую задачу.

Работай по задачам OpenSpec, а не придумывай собственный план вместо них.

После завершения задачи отметь её выполненной в tasks.md.

Не отмечай задачу выполненной, если реализация или необходимая проверка не завершены.

Если обнаружено противоречие между задачами, design и spec — остановись и сообщи об этом.

Работа с задачами и ветками

Задачи OpenSpec имеют иерархию:

1
├── 1.1
├── 1.2
└── 1.3

2
├── 2.1
├── 2.2
└── 2.3

Родительская задача 1 является группой, а не отдельной задачей реализации.

Работай с конкретными подзадачами 1.1, 1.2, 1.3 и т.д.

Не переходи к следующей группе задач, пока текущая группа не завершена, если OpenSpec не требует другого порядка.

Если работа ведётся в отдельной Git-ветке для группы задач, изменения должны оставаться в рамках этой ветки.

Не смешивай реализацию нескольких независимых задач в одну ветку без необходимости.

Порядок работы

Для каждой задачи:

Прочитай связанные требования OpenSpec.

Проверь существующий код.

Определи минимальное изменение.

Реализуй задачу.

Запусти необходимые проверки.

Исправь найденные проблемы.

Отметь задачу выполненной.

Перейди к следующей задаче.

Не выполняй следующие задачи заранее только потому, что их реализация кажется удобной.

Если задача требует изменения архитектуры, сначала проверь design.md и spec.md.

Каждая подзадача (вида 1.1, 1.2 и т.д.) должна выполняться отдельным агентом.

Приступая к фазе (группе задач, например 1), сам создавай нового агента на каждую подзадачу этой фазы — не проси пользователя вручную открывать новую сессию или чат.

Не выполняй подзадачи фазы напрямую в контексте текущего агента — делегируй каждую подзадачу отдельному агенту и дожидайся её завершения, прежде чем переходить к следующей.

После завершения всех подзадач фазы подведи итоги выполнения фазы: что сделано по каждой подзадаче, результаты проверок и общий статус фазы.

Это не относится к исправлению ошибок или доработкам в рамках уже начатой подзадачи — они выполняются в том же агенте, где подзадача была начата.

Git

Изменения должны быть небольшими и логически связанными.

Не изменяй файлы, которые не относятся к текущей задаче.

Не выполняй destructive Git-команды без явного указания.

Не коммить секреты, .env и временные файлы.

После завершения каждой подзадачи (вида 1.1, 1.2 и т.д.) и успешной проверки создавай отдельный коммит с изменениями этой подзадачи, прежде чем переходить к следующей.

Сообщение коммита формируй в стиле Conventional Commits с указанием номера подзадачи OpenSpec, например: `feat(1.4): add .env to .gitignore`. Используй тип, соответствующий характеру изменений (feat, fix, chore, test, docs и т.д.).
